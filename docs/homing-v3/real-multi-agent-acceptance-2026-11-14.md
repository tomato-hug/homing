# 真实多 Agent 会议与行动项验收（2026-11-14）

## 测试范围与隔离

- 使用全新 `/tmp` Git 示例仓库、独立 Homing 数据目录和本机临时端口。Codex CLI 0.167.0-alpha.4.1 与 Hermes Agent 0.14.0 均通过真实启动器创建新会话；没有向用户已有会话发送消息。
- Hermes 使用 DeepSeek 模型和临时配置、临时安装的 ACP 依赖、临时会话数据库；验收二进制只在内存中注册真实 Hermes manifest，使用正式 ACP 驱动、会议室和派发实现，没有替身发言者，也没有改用户的适配器配置。生产环境如需使用 Hermes，仍需自行配置对应适配器与依赖。
- Codex 会议会话使用 `read-only` 沙箱，Codex 行动项使用 `workspace-write` 沙箱。Hermes 进程使用 macOS 沙箱，拒绝读取用户主目录，写入范围限制为本次临时目录；通过独立探针确认了目录外读取被拒绝及目录内写入可用。
- Claude 在独立临时配置下可以检测到登录，但真实模型请求超时，诊断发现当前配置的服务端返回 503，因此本次没有把 Claude 计作通过。WorkBuddy 的现有新建会话入口可能复用活跃会话，未用于本次验收。原有 Claude 配置文件的校验值未改变。

## 实测结果

- 暂停会议、发送带 @Hermes 的消息、恢复：通过；Codex 与 Hermes 各自在新会话按顺序真实发言，Codex 复用自身测试会话生成纪要。
- 从纪要选择两个行动项，分别派发至 Codex 和 Hermes：通过。Codex 在独立 worktree 创建合成验收文件并核对内容，Hermes 在另一独立 worktree 返回合成验收结果；两次相同的派发重试没有创建额外任务或工作区，原测试仓库保持不变。
- 首次验收发现：没有完成钩子时，会议通过静默兜底收下 Codex 的回答并结束，但其会议派发记录仍显示运行中。修复后只有会议收到的回答与该会话、工作目录和原生完成回合的结果一致时，才补齐派发状态及结果；已处于等待用户、取消或失败状态的记录不会被此补偿主动覆盖；补偿限定在本次派发 ID，避免误更新使用同一会话的其他记录。
- 后续真实复测发现 Codex 将行动项写成 Markdown 表格，旧解析器只接受列表而漏掉两项。现可识别带任务列的表格并保留负责人和验收标准，沿用旧列表的行动项 ID，表格使用独立 ID；针对那份真实生成的表格纪要重启服务后，两个行动项均成功派发并完成。
- 修复后重新运行了真实 Codex＋Hermes 会议和两项派发，确认会议派发与两个行动项均完成。无钩子时会议仍保留原有静默检测等待，可能产生数十秒延迟。
