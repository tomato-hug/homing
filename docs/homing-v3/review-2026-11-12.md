## 0. 摘要

**目標（與用戶對齊後的一句話）**：Homing 是跨廠商的 agent 會話管理層。手機端是專業的會話管理端，在手機上對各家 agent 的會話做到和電腦前一樣的操作；電腦端是對標並超越 Magpie 的平台化管理端。亮點是跨 agent 協作：會話內 `@` 其他 agent，以及新增的「會議室」。

**現況**：v3 的後端、控制台和安卓大部分功能已寫完並有測試（見 `acceptance.md` §2），但有三件事擋住用戶的真實體驗：

| # | 問題 | 後果 |
|---|---|---|
| 1 | 267 個檔案、約 2.7 萬行改動全部未提交 | 一次誤操作或換機就丟；其他人 clone 不到 |
| 2 | 手機仍連 18787 上的 **Node** 中繼，Go 版從未在真實連線上運行 | 手機 0.9.0 的首頁分區、`@` 派發、雲端遙控等新功能在真機上用不到或行為不一致；用戶看到的問題有一部分來自這個錯配 |
| 3 | 從安裝到可用至少要十幾步手動操作，且倉庫私有、沒有 Release | 只有開發者本人能用起來，離「點、點、點」很遠 |

**本文新增的工作**（按優先級，細節見 §7）：

1. 提交基線，切換到 Go（P0）。
2. 手機與控制台的版面、文案、灰鴿動效整改（P1）。
3. 一條龍安裝與配對（P1–P2）。
4. Agent 適配補強：Codex 改走 app-server、Claude 活躍會話改走 Channels、逐家真機能力驗證（P1–P2）。
5. 會議室（P2–P3）。

**用戶已定的四個決定**見 §8。

### 2.3 灰鴿動效

**結論：設計好的 v2 動效沒有接入任何一端。**

- 設計規格在 `docs/homing-v2/pigeon_v2.json`：8 個場景（收信 recv、寄出 send、輕點 tap、喚醒 wake、等你處理 wait、離線 sleep、配對成功 pair、出錯 error），每個場景有觸發條件、使用位置、觸感回饋，另有頸環四色狀態（青＝正常、琥珀＝等待、紅＝出錯、灰＝離線）。
- 安卓使用的是 `res/raw/pigeon.json`，它是 v1 格式，只有 idle、flap、arrive_then_idle、bob_once、static 五種狀態。`HomingPigeon.kt` 只解析 v1 的 `states`，沒有讀 `scenes` 和 `neck_state`。
- 控制台只用一張靜態剪影（`console/src/lib/icons.ts` 的 `pigeonSilhouette`）。桌面托盤的序列幀已生成（`internal/gui/assets/tray/`，50 個檔案），這部分是唯一落地的 v2 內容。

**整改**：

1. 把 `pigeon_v2.json` 放進 `res/raw/pigeon_v2.json`，`HomingPigeon` 增加 `PigeonScene` 參數，按 v2 的 stage、pivots、keys 播放；保留 v1 狀態作為相容。
2. 頸環顏色做成獨立參數，由連線狀態和待處理數驅動。
3. 觸發點按 v2 的 `used_in` 逐一接上：

| 場景 | 手機觸發點 | 觸感 |
|---|---|---|
| recv | 首頁收到 P0／P1 新消息（30 秒內合併只播一次）、通知展開頁 | 落地幀 CONFIRM |
| send | 回覆、批准、拒絕在服務端確認之後；確認前保持銜信姿態 | 起跳幀輕觸 |
| tap | 「我的」頁品牌標、下拉刷新鬆手 | 無 |
| wake | 重新連上電腦 | 無 |
| wait | 首頁「等你處理」分組頭，`waiting > 0` 時循環 | 無 |
| sleep | 首頁連線卡：斷線超過 30 秒、電腦睡眠、暫停推送 | 無 |
| pair | 「添加電腦」完成頁 | 落到手機那一幀給成功觸感 |
| error | 錯誤提示條、發送失敗的消息 | 出現感嘆號時 REJECT |

4. 控制台用同一份 JSON 在 SVG 上播放（`console/src/lib/pigeon.ts`），用在總覽、設定精靈第 3 步、空狀態。
5. 系統「減少動態效果」開啟時全部停在最後一幀，只保留頸環顏色（v2 的 `reduced_motion` 規定）。

### 2.4 讓 agent 能「看見」手機界面

目前安卓只有 Robolectric 單元測試，沒有截圖。接手的 agent 看不到真實版面，這也是版面問題反覆出現的原因之一。

- 加入 Roborazzi（基於 Robolectric 的 Compose 截圖測試，不需要模擬器）。為首頁、會話頁（含長消息、圖片失敗、工具摘要）、模型面板、新建會話、配對頁各錄一組基準圖。字體縮放取 1.0 和 1.3，寬度取 360 dp 和 411 dp。
- `./gradlew verifyRoborazziDebug` 進 CI。改版面時 agent 必須附上前後對比圖。
- 控制台已有 Playwright 驗收，把 390 px 和 1440 px 的截圖也納入基準。

### 3.2 目標流程

**電腦端（目標：裝完 3 次點擊）**

1. 下載 `Homing.dmg`（macOS，已簽名公證）／`Homing-Setup.exe`（Windows）／一行安裝命令（Linux、遠程開發機）。
2. 打開 App，自動完成：
   - 啟動本機服務並預設開啟開機自啟（設定頁可關）。
   - 偵測到舊的 Node 中繼（LaunchAgent `dev.agentpush.relay`）時，彈窗說明並一鍵遷移：備份 plist、卸載、Go 版接管 18787、保留「回到舊版」按鈕 7 天。
   - 掃描已安裝的 agent，預設全選「接入」；一次點擊安裝所有鉤子（每個檔案先備份）；需要重啟的 agent 列出來，能代為重啟的提供「重啟」按鈕。
3. 引導頁第二屏只顯示**一個二維碼**（見下）和「離開 Wi‑Fi 也能用」開關。

**手機端（目標：掃一次碼）**

1. 用手機相機掃電腦上的二維碼。二維碼內容是 `http://<局域網IP>:18787/get?pair=<一次性令牌>`。
2. 這個落地頁判斷：
   - 已裝 App：用 `homing://pair?...` 深連結直接打開 App 的配對確認頁。
   - 沒裝：顯示「下載 Homing」按鈕（局域網直傳 APK），以及按品牌給出的「允許安裝未知應用」圖文步驟。安裝後首次打開，App 讀取剪貼板或落地頁寫入的令牌，直接進入配對確認，不用再掃一次。
3. 配對成功（播放 pair 動效）後，按順序引導：通知權限 → 忽略電池優化 → 國產 ROM 自啟動頁（小米、華為／榮耀、OPPO、vivo 各給跳轉 Intent 和圖示）。每一步都能跳過，跳過的項目在「我的」頁留一張待辦卡。

**遠程（離開 Wi‑Fi）**：已定官方中轉為預設、自建為進階（§8）。無論哪種方案，手機端都已有雲端 RPC（`CloudTransport.kt`），只差服務端地址和電腦端的一鍵開啟。

## 4. 方向三：會議室

### 4.1 與現有協作的區別

| | 會話內 `@`（已有） | 會議室（新增） |
|---|---|---|
| 主體 | 一個父會話，子任務掛在下面 | 一個獨立的「房間」，多個 agent 平等參與 |
| 上下文 | 子任務冷啟動，只拿到派發時打包的上下文 | 共享一份會議紀錄，每輪發言前補發「上次發言後的新內容」 |
| 記憶 | 無 | 房間級記憶檔（決議、待辦、已知事實），所有參與者可讀，按規則可寫 |
| 結果 | 結果卡回到父會話 | 會議紀要 + 決議 + 行動項；行動項可一鍵轉成派發任務 |
| 寫文件 | 可寫（有 worktree 隔離） | 預設只讀討論；要動手時轉成派發任務 |

### 4.2 參考項目與可借鑑點

| 項目 | 做法 | 借鑑 |
|---|---|---|
| Karpathy `llm-council` | 三階段：各模型獨立作答 → 匿名互評排序 → 主席綜合成最終答案 | 「議會模式」直接照搬三階段；匿名互評防止按身份偏袒 |
| `yogirk/agent-council`、`0xNyk/council-of-high-intelligence`、`dinhkarate/llm-roundtable` | 讓 Claude Code、Codex、Gemini CLI 等本機 CLI agent 帶著代碼庫上下文開會；用已有訂閱，沒有額外 API 費用；llm-roundtable 引用研究指出多 agent 辯論的收益主要來自多數投票 | 參與者就是用戶本機已接入的 agent，不另接 API；提供「投票」收尾方式 |
| AutoGen `SelectorGroupChat` / `RoundRobinGroupChat` | 每次發言廣播給全員；由模型根據上下文和成員描述選下一位發言者；預設不讓同一人連續發言；用「提到 TERMINATE」「最多 N 條消息」等終止條件 | 主持模式的選人邏輯、成員描述、終止條件 |
| Claude Code Agent Teams | 組長 + 隊員，各自獨立上下文；共享任務清單；隊員之間通過信箱直接發消息；協調全部基於本機檔案 | 會議室的「行動項」就是共享任務清單；房間資料用檔案存，方便 agent 直接讀 |
| Codeg（多 agent 工作區） | `@` 一個 agent 就委派子任務；子會話冷啟動、只看到任務文本；預設委派深度 1；`@` 只是強指令，最終由主 agent 決定 | 會議室裡 agent 之間 `@` 也要有深度和次數上限；不能假設 agent 一定照做 |
| AgentBridge | Claude Code 與 Codex 在同一工作流裡互相推送消息；每條消息帶 `source` 字段，橋接器不會把消息轉回來源，防止循環 | 每條房間消息帶來源，轉發時排除來源，防止 agent 互相無限回覆 |

### 4.3 方案

**核心概念**

- **房間（Room）**：`id`、標題、議題、工作目錄（可選，決定 agent 能讀哪個代碼庫）、參與者、模式、狀態（籌備／進行中／暫停／已結束）。
- **參與者**：一個已接入且 `capabilities.new_session` 或可驅動的 agent + 一個角色（例如「架構」「審查」「唱反調」）+ 可選模型。用戶本人也是參與者。每個 agent 參與者在房間裡對應一個**真實的原生會話**（在房間工作目錄裡新建），這樣它的思考、工具調用都可在原會話中查看。
- **會議紀錄（transcript）**：Homing 自己維護的消息序列，存 `<資料目錄>/rooms/<id>/transcript.jsonl`。
- **房間記憶**：`<資料目錄>/rooms/<id>/MEMORY.md`，分「背景」「已達成共識」「分歧」「待辦」四節。主持人（或用戶）每輪結束時更新；參與者通過 MCP 工具提議修改，由主持人或用戶採納。
- **紀要**：會議結束時生成 `MINUTES.md`：議題、結論、各方立場、行動項（負責 agent + 驗收標準）。

**發言模式**（建房時選，進行中可切換）

| 模式 | 流程 | 適用 |
|---|---|---|
| 輪流 | 按參與者順序各發言一次為一輪；用戶可設輪數 | 方案評審、多視角意見 |
| 主持 | 主持人（用戶或指定 agent）每次點名下一位；agent 主持時用 SelectorGroupChat 的選人方式，不連續選同一人 | 有明確流程的討論 |
| 議會 | 各 agent 並行獨立作答 → 匿名互評 → 主席綜合（llm-council 三階段） | 技術選型、需要獨立判斷的問題 |
| 自由 | 任何 agent 可在發言中 `@` 另一位；用上限防失控 | 頭腦風暴 |

**上下文怎麼共享**（關鍵細節）

CLI agent 不能共用一個上下文窗口，所以「共享上下文」由 Homing 拼裝：

1. 每個參與者第一次發言時，Homing 發給它的提示包含：房間議題、參與者名單與角色、`MEMORY.md` 全文、到目前為止的會議紀錄（超過預算時用滾動摘要）、發言規則（長度上限、需要表態時用固定格式）。
2. 之後每次輪到它，只發「它上次發言之後的新消息」+ 當前 `MEMORY.md` 的變更部分，靠它自己的原生會話保留之前的內容。
3. 會議紀錄超過預算（預設 30k 字元）時，主持人生成滾動摘要寫入 `MEMORY.md` 的「背景」節，新加入者只讀摘要。
4. 同時通過 `internal/mcpserver` 給參與者三個工具：`room_read`（讀紀錄或記憶）、`room_post`（發言或 `@` 某人）、`memory_propose`（提議修改記憶）。agent 不支持 MCP 時退回純提示注入。

**防失控**

- 每條消息帶 `from`，轉發時不送回來源（AgentBridge 的做法）。
- 上限：每輪每人最多一次發言；自由模式下 agent 之間 `@` 深度預設 1、全場最多 20 條 agent 消息；每個房間有 token 或時間預算，到達後自動暫停並通知用戶。
- 終止：主持人或任一 agent 輸出約定的結束標記、達到輪數、用戶點「結束」。
- 安全：預設所有參與者以只讀／計劃模式啟動（Codex `--sandbox read-only`、Claude `--permission-mode plan`，其他 agent 按能力表選最保守模式）；要寫文件必須經用戶把行動項轉成派發任務（走現有 `/api/compose` 和 worktree）。agent 發言一律當不可信文本，不自動執行其中的命令。

**手機界面（單獨分頁「會議室」）**

- 底部導航增加第四個分頁「會議室」（收件箱／會話／會議室／我的）。
- 列表：進行中的房間在上，顯示正在發言的 agent 頭像和灰鴿 wait 動效；已結束的折疊在「歷史會議」。
- 建房：選議題（可從一個已有會話「拉人開會」，自動帶入該會話摘要）、勾選參與者（只列出可新建會話的 agent）、指定角色、選模式、選工作目錄。
- 房間頁：群聊樣式，每個 agent 用自己的品牌頭像和顏色；頂部參與者條顯示誰在說話、誰在排隊；底部操作列「點名／下一輪／暫停／結束」；右上角「記憶」和「紀要」兩個抽屜；長按某條發言可「採納為共識」「轉成行動項」。
- 推送：輪到用戶表態、會議暫停（預算用完）、會議結束時各推一次，其餘不推。

**電腦端**：控制台新增「會議室」頁，三欄：房間列表／會議紀錄／記憶與紀要；支持把會議紀錄投到大屏。

**接口草案**

| 方法 | 路徑 | 說明 |
|---|---|---|
| POST | `/api/rooms` | 建房：議題、cwd、參與者（agent、角色、模型）、模式、預算 |
| GET | `/api/rooms`、`/api/rooms/{id}` | 列表與詳情（含參與者狀態） |
| GET | `/api/rooms/{id}/messages?after_seq=` | 會議紀錄；SSE 事件 `room_message`、`room_state` |
| POST | `/api/rooms/{id}/messages` | 用戶發言（可 `@`） |
| POST | `/api/rooms/{id}/control` | `next`、`call:<agent>`、`pause`、`resume`、`end`、`switch_mode` |
| GET/PATCH | `/api/rooms/{id}/memory` | 讀記憶；採納或拒絕 `memory_propose` |
| POST | `/api/rooms/{id}/actions/{n}/dispatch` | 把行動項轉成派發任務 |

**實作位置**：新目錄 `internal/room`（狀態機、提示拼裝、調度），複用 `internal/driver`（ACP）、各 agent 的 `SessionStarter` 和 `Replier`、`internal/orchestrator` 的 mention 解析、`internal/live` 的條目流。

**分期**

| 期 | 內容 | 驗收 |
|---|---|---|
| R1 | 輪流模式；Codex + Claude 兩家；只讀；手機與控制台的列表、房間頁、結束生成紀要 | 真機開一場 2 人 2 輪的會，紀要正確列出雙方立場；用戶在手機上能點名、暫停、結束 |
| R2 | 主持、議會模式；房間記憶與 `memory_propose`；行動項轉派發；從已有會話「拉人開會」 | 議會模式三階段在手機上分步可見；行動項派發後結果回到房間 |
| R3 | 自由模式；所有可驅動 agent（ACP）；預算與自動暫停；控制台投屏 | 自由模式在上限內自動停止；ACP agent 至少一家完整參與 |

| 3 | 會議室第一版 | **只做討論和紀要** | R1 範圍不變：參與者只讀或計劃模式；寫代碼只能把行動項轉成派發任務 |
| 4 | 切換到 Go | **隨時，由開發推進安排** | 已提供 `scripts/switch-to-go.sh`（失敗自動切回）和 `scripts/rollback-to-node.sh` |

**切換前發現並已修正的問題**：Go 版的 `serve`、桌面模式和開機自啟都只監聽 `127.0.0.1`，但向手機宣告的局域網地址是 18787，手機在局域網連不進來（之前的驗收都在本機瀏覽器上做，沒有覆蓋這點）。已改為與 Node 一致的 `0.0.0.0:18787`；所有 `/api` 仍要求令牌，`/console` 和 `/api/autostart` 仍只接受本機請求。其餘還寫著 18788 的預設值（`homing pair`、`requestPort`、`integrations/hooks` 模板、Dockerfile、`docs/self-host.md`）一併改為 18787。

**待辦**：桌面模式（`homing` 不帶參數）啟動時會自己再監聽 18787，與開機自啟的服務衝突。IN-3 需要讓桌面殼偵測到已有服務時直接連上它，而不是另起一個。
